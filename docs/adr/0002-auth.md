# ADR 0002 — Authentication, sessions and request security

- Status: accepted
- Date: 2026-10-08

## Context

We need email + password (with verification and reset) and Google OAuth, on Next.js 15 App Router,
deployable to Vercel serverless, with sessions that can be revoked after a password reset.

## Decision

**Auth.js v5 (`next-auth@5.0.0-beta.32`)** with the Credentials and Google providers and **JWT sessions**.

- Auth.js' Credentials provider only supports JWT sessions, so we use them for both providers. To make
  JWTs revocable, the token carries `User.sessionVersion`; `getCurrentUser()` re-reads the user on every
  request and rejects tokens whose version no longer matches. A password reset bumps the version, which
  signs the user out everywhere.
- **No Prisma adapter.** The adapter dictates its own `User`/`Account`/`VerificationToken` schema
  (e.g. `emailVerified`, not our `emailVerifiedAt`). We resolve OAuth users ourselves in the `jwt` callback
  (`resolveOAuthUser`) with a small `Account` table. An existing password account is linked to Google
  only when Google asserts `email_verified`.
- **Passwords:** argon2id via `@node-rs/argon2` (prebuilt binaries, no node-gyp on Vercel) with OWASP
  parameters (m=19 MiB, t=2, p=1). Unknown emails still run a dummy verify to equalise timing.
- **Email verification & reset tokens:** 32 random bytes, only the SHA-256 hash is stored (`AuthToken`),
  single use enforced by a conditional `UPDATE … WHERE usedAt IS NULL AND expiresAt > now()`. Verify links
  open a page with a _button_ (POST), so mail scanners that prefetch links cannot burn the token. Issuing
  a new token invalidates older ones. Sign-up and reset are enumeration-safe.
- **Invite sign-up:** an invite link proves inbox ownership, so an account created through it starts
  verified and joins the inviting workspace (email must match the invite).
- **Split config:** `server/auth.config.ts` (provider-free) is used by the middleware to decode the JWT;
  `server/auth.ts` adds providers and callbacks. Middleware runs on the Node.js runtime (stable in Next 15.5)
  so it can check workspace membership with Prisma.

## Rate limiting

Fixed-window counters in Redis (atomic Lua `INCR` + `PEXPIRE`), defined in one table (`RATE_LIMITS`):
login 5/15 min per IP+email, sign-up 5/h per IP, reset 3/h per IP+email, verification resend 3/h,
writes 60/min per user (all `/api/v1` mutations and server actions). The limiter fails **open** if Redis is
down (logged at `error`) — availability over strictness for a B2B tool; revisit for high-risk endpoints.

## CSRF review

| Surface                                 | Protection                                                                                                                                                   |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Server actions (auth, onboarding forms) | Next.js compares `Origin` with `Host` for every action POST                                                                                                  |
| `/api/v1/*` (cookie-authenticated JSON) | `assertSameOrigin`: unsafe methods require a same-origin `Origin` (or `Sec-Fetch-Site: same-origin`); JSON content-type required; cookies are `SameSite=Lax` |
| Auth.js endpoints (`/api/auth/*`)       | Auth.js double-submit CSRF token                                                                                                                             |
| Stripe webhook                          | No cookies; HMAC signature over the raw body                                                                                                                 |

## Security headers

Per-request nonce CSP from middleware (`script-src 'self' 'nonce-…' 'strict-dynamic'`, `frame-ancestors 'none'`,
`object-src 'none'`, `form-action 'self' https://accounts.google.com`), plus HSTS (2 years, preload),
`X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, COOP. A nonce CSP
requires dynamic rendering, so the root layout reads request headers. Sentry is tunnelled through
`/monitoring` so `connect-src` stays `'self'`.

## Consequences

- One DB read per authenticated request (user + sessionVersion) — acceptable, indexed by primary key.
- Auth.js v5 is still tagged beta; the version is pinned and wrapped behind `server/auth.ts` and
  `server/services/session.ts`, so a swap (e.g. to Better Auth) stays local.
